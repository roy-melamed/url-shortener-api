## Autonomous delivery safeguards (2026-10-28)
This policy replaces all earlier requirements for human PR merge approval.
1. Ryan implements and records test results in GitHub, then routes every PR to Dwight. Ryan never merges.
2. Dwight reviews every PR's exact current head SHA, including workflow changes. Use a submitted APPROVE review when a distinct authorized account permits it. With the shared account, submit a COMMENT review containing "[dwight] Technical verdict: PASS" (or FAIL/BLOCKED), full head SHA, findings, and evidence links. COMMENT is a technical verdict, never a formal GitHub approval. Michael must verify it came from Dwight's actual assigned Herdr session and matches the submitted review URL and current head SHA; a copied signature, label, Jira comment, or PR author assertion is insufficient. If provenance cannot be verified, stop. New commits invalidate the verdict. All blocking findings must be resolved and review threads resolved.
3. Michael may merge without human merge approval only after verifying Dwight's current verdict, no conflicts, and successful completed required CI on the current PR revision/test merge against current main. Require CI / quality and actual successful lint, typecheck, coverage tests, and build; missing, queued, pending, skipped, neutral, cancelled, stale, or failed results block merging. Recheck head/base and use an expected-head SHA lease on the merge. No admin bypass, force push, disabling checks, or direct push to main. If the base changes, update and rerun checks/review as needed. Do not enable unattended GitHub auto-merge until a separately authenticated required Dwight gate exists: the shared account cannot enforce role identity. Michael performs the verified automatic merge.
4. After merge, Michael sends Pam the actual resulting main commit SHA and PR link. Pam uses a clean detached checkout of that exact merged commit, confirms it belongs to main, runs the available automated suites and acceptance/negative checks in local or nonproduction environments, and records executed commands, exit codes, acceptance coverage, defects and risks in a linked GitHub report/artifact. Premerge evidence alone never passes QA. On FAIL/BLOCKED, keep out of Evidence Review and send rework through Ryan and Dwight.
5. Pam alone posts the final concise Jira acceptance evidence and moves the issue to Evidence Review on PASS. Discover transitions; set configured Agent Owner to Human for Evidence Review. No other agent posts final acceptance evidence or makes that transition. Michael/Ryan/Dwight keep technical reports in GitHub; Jira comments only for material blockers or human decisions. Pam updates her existing milestone instead of duplicates. Format: attribution line, blank line, then 1-4 short lines with PASS/FAIL/BLOCKED, acceptance summary, PR and durable QA/CI evidence links. The linked report identifies the tested merged SHA.
6. Evidence Review -> Done is human-only. No agent ever performs this transition, even after a human says evidence looks good; ask the human to move it. Production deployment requires explicit human approval for the exact artifact/commit and target environment. A PR merge or Jira acceptance never authorizes production deployment. Never deploy as part of CI or QA. Missing access, unavailable acceptance tests, invalid transitions, or missing evidence must remain visible blockers.
Shared credentials enforce these role boundaries by agent policy, not account-level identity. Never claim that a signature alone provides independent reviewer authentication.
